# neck-project 需求梳理

## 1. 第一阶段项目目标
第一阶段只聚焦一个目标：

> 把 `neck-soccer` 做成一个**偏游戏感、接近成品**的网页顶球游戏。

这意味着：
- 当前不再把 `neck-project` 当作双主线实验项目推进
- `neck-archive` 暂时降级为参考原型，不作为当前主线交付
- 第一阶段重点不是展示 head-tracking 技术，而是交付一个普通用户能直接理解、开始、游玩、失败、重开的完整小游戏

第一阶段的核心输入定义为：
1. **位置移动**：头部在画面中的左右 / 上下移动
2. **姿态变化**：点头、抬头、低头、转头等动作变化

这两类输入都需要进入最终交互，而不是只做单纯的“头部位置跟随”。

## 2. 子项目需求

## 2.1 Neck Soccer

### 2.1.1 核心目标
让用户出现在摄像头画面中，通过“真实识别到的人脸/头部区域”与足球发生碰撞，完成顶球游戏。

### 2.1.2 当前已具备功能
#### P0 - 核心可玩能力
- 调用前置摄像头并显示实时画面
- 通过 MediaPipe FaceMesh 识别人脸关键点
- 推导头部中心位置与头部碰撞半径
- 用头部区域与球进行碰撞判定
- 足球具备重力、速度、反弹、速度上限等基础物理逻辑
- 球掉出底部边界后判定本轮失败
- 有基础游戏循环（IDLE / PLAY / OVER）

#### P1 - 体验增强
- Demo 模式（鼠标替代）
- 顶球闪光反馈
- 提示文案与模式状态显示
- 初始 neutral pose 校准
- 全屏摄像头背景

### 2.1.3 当前核心问题
#### P0 问题
1. **“识别到的人”与“碰撞体”是否真正一致，仍需实机验证**
   - 代码上已经从鼻尖改为整颗头，但目前仍缺少“可视化调试层”去证明碰撞体是否完全贴合真人头部轮廓。
2. **`camReady` 变量存在残留引用风险**
   - 当前代码中 `camReady = true;` 仍然出现，但变量声明已不在文件里，属于明显的遗留问题。
3. **FaceMesh 初始化链路虽然补全，但缺少失败分层策略**
   - 比如：模型加载失败、摄像头授权失败、识别成功但无脸、识别抖动等状态还没有完全拆开处理。

#### P1 问题
1. 头部碰撞体还是“圆形近似”，不是真实轮廓。
2. 缺少难度机制、连击机制、音效反馈。
3. 缺少面向产品化的玩法目标（计时、关卡、排名、训练模式）。

### 2.1.4 用户视角评估
- **满足了什么**：已经初步满足“用摄像头识别人，并让人脸/头部与球发生交互”这个核心方向。
- **没完全满足什么**：用户最在意的是“我在镜头里看到的自己，是否真的在和球碰撞”。这件事现在逻辑上接近成立，但产品反馈层还不够强，导致用户仍会怀疑系统没有真正识别到自己。

### 2.1.5 Neck Soccer 优先级建议
#### P0（必须先解决）
- 增加碰撞体可视化调试层（显示 head center / radius / landmarks 轮廓）
- 修正残留变量和潜在运行错误（如 `camReady`）
- 重新验证“摄像头画面 → 识别结果 → 碰撞体 → 球反弹”的完整链路

#### P1（接下来增强）
- 提升头部轮廓拟合精度（圆形 → 椭圆/多边形）
- 增加关卡、难度、连击、音效
- 增加稳定性平滑和抗抖算法

#### P2（更后面）
- 做成训练产品：颈部活动度训练、反应训练、康复小游戏
- 成绩记录、本地历史、排行榜

## 2.2 Neck Archive（当前暂停为主线）

### 2.2.1 当前定位
调用前置摄像头，识别头部姿态（yaw / pitch / roll / offset），再用这些姿态驱动一个沉浸式视觉世界，让用户“用头去导航页面”。

但在当前阶段，它只保留为参考性视觉原型，不再作为第一优先交付目标。

### 2.2.2 当前已具备功能
#### P0 - 核心能力
- 调用前置摄像头
- 识别人脸关键点
- 估算头部 yaw / pitch / roll / N offset
- 用姿态驱动 Three.js 粒子与线框场景
- 提供基础 HUD（Axis / Camera / Mesh / Reality / content 切换）
- 多 campaign 视觉主题切换

#### P1 - 体验增强
- 摄像头实时背景 + Mesh 叠加
- Reality / Mesh 图层开关
- tracking / no face 状态文本
- immersive HUD 风格

### 2.2.3 当前核心问题
#### P0 问题
1. **识别链路没有显式 `initialize()` 阶段**
   - 当前 `neck-archive` 中 FaceMesh 的用法与 `neck-soccer` 不一致，需要验证是否存在同类初始化隐患。
2. **项目目标尚不够聚焦**
   - 现在它更像“技术演示页”，而不是一个完成度高的产品。
3. **头部姿态与业务任务之间的映射偏弱**
   - 用户能“看着玩”，但还没有一个强目的性任务，例如浏览内容、完成操作、驱动某种故事结构。

#### P1 问题
1. 缺少真正的内容层，而不只是视觉粒子层。
2. 缺少 mobile/desktop 差异适配策略。
3. 缺少性能监控与降级策略。

### 2.2.4 用户视角评估
- **满足了什么**：已经满足“调用摄像头 + 识别姿态 + 驱动视觉场景”的技术展示目标。
- **没完全满足什么**：从用户角度看，它目前的“可玩性 / 可用性 / 业务意义”还比较弱，更像一个漂亮 demo，而不是一个明确有用的产品界面。

### 2.2.5 Neck Archive 优先级建议
#### P0
- 明确这个页面到底是“视觉演示”还是“可导航内容产品”
- 验证 FaceMesh 调用链的一致性和鲁棒性
- 梳理姿态参数到场景行为的映射表

#### P1
- 加入真实内容层（卡片、章节、节点、热点）
- 强化主题切换的差异，不只是换颜色
- 加性能降级与 loading 状态

#### P2
- 扩展成品牌互动页、展览页、训练页或沉浸式故事界面

## 3. 第一阶段交付要求（以 Neck Soccer 为主）

### 3.1 P0：必须完成
- 清晰的开始页、开始、游玩中、失败结算、重开流程
- 头部碰撞体与真人位置基本一致
- 同时支持“位置移动 + 姿态变化”双输入模型
- 明确的人脸追踪状态反馈（初始化失败 / 无脸 / 追踪中 / 丢失）
- 基础但可信的命中反馈与得分反馈
- 保留适量 debug，但只服务于“识别是否可信”而不是开发者展示

### 3.2 P1：第一阶段增强
- 更强的命中反馈、连击、难度渐进
- 从圆形碰撞体进一步优化为椭圆/更贴近头型
- 更自然的新手引导与更强的游戏感
- HUD 正式态收敛，技术型调试信息进一步后退

### 3.3 P2：后续再做
- 排行榜、分享、多模式
- 康复/训练产品化包装
- archive 重新纳入主线
- 大规模模块化重构

## 4. 统一项目需求（cross-project）

### 3.1 共享 P0 需求
- 统一摄像头权限申请与错误提示
- 统一 FaceMesh 初始化与状态管理
- 统一 landmark → head model 的计算逻辑
- 统一 debug 能力（是否检测到脸、关键点、碰撞体、姿态值）
- 统一 fallback 逻辑（demo mode / no camera / offline）

### 3.2 共享 P1 需求
- 统一 UI/HUD 视觉系统
- 统一事件系统（开始、暂停、重置、失败、追踪中断）
- 统一性能监控与 render loop 管理

### 3.3 共享 P2 需求
- 模块化重构，摆脱单文件 HTML
- 支持多场景复用（游戏、训练、展览）
- 为后续产品化预留埋点和配置能力

---

## 5. 总结判断
当前 neck-project 的第一阶段主线已经明确：

> **先把 `neck-soccer` 做成一个偏游戏感、接近成品的顶球网页游戏。**

这意味着：
- `neck-soccer` 是当前唯一第一优先交付对象
- `neck-archive` 暂停为主线，只保留参考价值
- 当前最重要的不是继续发散技术实验，而是收敛成一个普通用户能直接感知、理解并愿意反复玩的单玩法小游戏

后续所有功能梳理、UI/UX 优化和开发取舍，都应围绕这个目标进行。
