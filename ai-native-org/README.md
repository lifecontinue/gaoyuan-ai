# AI Native 组织基建

装几个插件，不会让团队变成 AI Native。真正卡住的通常是：上下文到不了现场、Agent 权限说不清、改完行为没人写回文档。

这份笔记把经验收成一套可复制的做法。工具名可以换，职责尽量别丢。写的时候刻意把「仓库里已经能跑的」和「值得继续建的」分开——混在一张图里，读起来会像已经全部上线。

---

## 两套东西，别画成一张图

**编码 Agent** 已经能当半个同事用：规则写在仓库里，改代码、跑检查、更新文档、开 PR。这是目前最稳的控制面。

**产品里的 Copilot** 是另一套运行时：对话 SDK、线程、页面上下文、功能开关、模型观测。它服务用户，不是给 Slack 回帖的那个 Bot。

**组织总线** 多数团队还没打通：反馈自动进任务、会前材料自动齐、密钥统一出口、入离职自动收权限。下面会写怎么建，但那是蓝图，不是现状。

任务系统用 Linear、Jira 还是 GitHub 都可以。工程交付建议认准一个面：PR。再搞第二套「唯一真实来源」，会议里还是会对不上。

---

## 分层

从上到下看即可。标了「蓝图」的，先别写进 onboarding 当成已上线。

```text
入口        编辑器里的编码助手 · 产品 Copilot · 以后才是 Slack Bot
编排        产品侧：对话 SDK + 页面总线
            组织侧：工作流引擎、日历触发（蓝图）
模型        流式接口；统一网关和计费（蓝图）
观测        对话 trace 往往已经有了；评测门禁、审计还要补
交付        PR、自动检查、功能开关
数据        业务库、CMS、数仓；Agent 不要直连原始层
知识        仓库文档 + 给 Agent 的规则（现成）
            会议/聊天入库（蓝图）
密钥        保险库 + 分环境 secret
            逻辑 key 网关（蓝图）
纪律        高风险先问人；改了业务规则，文档跟 PR 一起走
```

横切还有 CRM、人事、合同。有系统就接只读；写操作默认等人确认。

---

## 编码 Agent：把交活写进仓库

给模型的说明要分层。根目录管流程（能不能直接提交主干、验证跑到什么程度、文档算不算交付）。各应用目录管框架、测试命令、模块边界。某个 Copilot 功能再单独写一份，避免所有人读同一份几千行的总规。

交活可以短成这样：

1. 尽量只动一个包，别为了方便横跨前后端。
2. 改完跑这个包最小的那组检查。全仓红了、但和这次无关，写清楚，别假装成功。
3. 业务规则、权限、状态机变了，同一份 PR 里改领域文档。没改也写一句「这次不涉及」。
4. 迁移、鉴权、计费、部署脚本，先问人。
5. 从最新主干拉分支，一次只做一件事。PR 里写摘要、怎么验的、文档动了没、还有什么风险。
6. 自动审查机器人指出的明确问题就改；拿不准的标给人看，别猜。
7. 留一份很短的工作记录：做了什么、怎么验的。不要把聊天原文和密钥贴进去。

知识库不是写给领导看的周报。Agent 下次还要靠它判断「这个角色能不能看见那条数据」。地图页、领域页、变更日志分开：地图负责指路，领域页写具体规则，日志只追加。

## 产品 Copilot：别和组织 Bot 混进程

用户侧助手常见会有：通用对话、某条引导流程、某个岗位的专用入口。入口不同，提示词、工具、能否生成文档都不一样。

上下文建议至少三种：当前服务的对象、手头文档、用户正在看的页面。页面正文最好在发送时再取，不要整段塞进本地持久化——又大又容易漏敏感信息。

实现上不必上很重的图编排。一套对话 SDK、流式接口、线程存在业务 API 里，就够跑很久。页面和助手之间用很薄的事件/请求总线，比把 DOM 塞进 prompt 稳。

功能用开关控制，出问题能关。观测至少要能看到：提交、首 token、成功、失败。改提示词或路由，复杂的先拿几条真实例子回归，再放开流量。

---

## 组织侧：值得建、但别宣称已经有了

密钥今天多半是：保险库存厂商 key，本地和各环境从 secret 服务注入。问题是副本一散，吊销和计费就很难。下一步才是网关：应用只拿公司发的逻辑 key，原始 key 不出保险库。

身份也一样。人走 SSO；Agent 用短时机器凭证，scope 写窄。生产发布、对外发送，不要发给「闲聊就能调」的那个应用。

反馈是最值得先做的一条组织路径：

```text
频道里出现一条反馈
  → 归一化（类型、严重度、产品面、能不能复现）
  → 查重
  → 低把握就追问，高把握才建任务
  → 线程里回一句人话 + 链接
  → 涉及付款、安全、删数据：只建单和告警，不动生产
```

会议可以后做：开始前半小时把相关任务和上次结论推到频道；结束后从转写抽决策和 action，写进任务系统。抽出来的负责人如果只是模型猜的，标成未指定，别直接 @ 错人。

销售侧：会前读 CRM 做简报可以自动；改金额、关单、改阶段，默认要人点头。产品缺口送进同一条反馈管道。人事侧：入离职以 HR 系统为准开通和吊销；薪酬、Offer 正文不要进公开频道。合同和 Offer：模型只出草稿，发送和作废必须人审。

指标问答只允许跑已经审过的问题/看板，答案带上问题 ID。不要让 Bot 对数据湖写任意 SQL。

## 会议怎么接工具

一种会只做一件事。Standup 不评审需求，全员大会不定迭代范围。

会前工具把材料备齐，会中人拍板，会后写回任务和文档。没写进去的待办，就当没发生过。

| 频率 | 活动 | 人在会上干什么 | 工具会前/会后干什么 |
|------|------|----------------|---------------------|
| 每天 | Standup | 只谈阻塞和需要别人的事 | 会前贴进行中/阻塞/到期；会后改状态 |
| 每天 | 反馈消化 | 人只审边界和误判 | Bot 分类、查重、建单或追问 |
| 每周 | 需求评审 | 做、缓、砍 | 会前一页问题/验收标准/范围外；通过的进迭代 |
| 双周 | 进度同步 | 风险和跨队依赖 | 自动摘要，不要念看板 |
| 双周或按需 | 和业务/客户对齐 | 预期、承诺、待决策 | 一页纸；承诺进任务；客户场纪要回 CRM（人审） |
| 双周 | 提示词/评测回顾 | 决定升不升级 | 对比分数和坏例 |
| 每月 | 权限抽检 | 看差异要不要收 | 账号、密钥、入离职对账 |
| 每季 | 技术分享 | 方向和取舍 | 议题征集、录播、决策写回文档 |
| 持续 | 1:1 | 人和关系 | 内容默认不进公共 Agent |
| 偶尔 | 线下/offsite | 高带宽的事 | 会后必须回流，否则等于旅游 |

对齐外部干系人时，不要把内部看板念一遍。他们要的是：交付了什么、下一步、要他们拍什么板、上次答应的事有没有下文。

## Skill、MCP、Plugin

三个词经常被混用：

- MCP：模型能调的工具服务。
- Skill：什么时候用、先做什么、哪些绝对不能做。编码助手读的是仓库里的手册；组织 Bot 读的是另一套。
- Plugin：装到编辑器、Slack、文档产品里的包装。

不必追求「全公司共用同一套 MCP」。先让编码助手把仓库规则执行稳，再把 Slack、任务系统、日历做成内部 MCP。写操作默认要人点头。密钥解析不要进对话 Agent。

编码助手值得内置的几条：只动相关目录、最小验证、文档跟变更走、高风险停下来、PR 写清楚怎么验的。

反馈 Bot 值得内置的几条：脱敏、查重、低把握不建单、P0 打事故频道。

## 工具清单（复制时改名字，别删职责）

先有职责，再填你们已经买的产品。Owner 空着的先指定人。

| 职责 | 常见选择 | 备注 |
|------|----------|------|
| 员工登录 | Auth0、Okta、公司 SSO | 人和机器分开 |
| 密钥存放 | 1Password、Bitwarden | 聊天里不准传 |
| 模型/SaaS 出口 | 自建网关、LiteLLM、Portkey | 应用只拿逻辑 key |
| 审计 | 日志平台、数仓 | Agent 不能删自己的痕迹 |
| 协作 | Slack、Teams | 反馈和事故分开频道 |
| 任务 | Linear、Jira、GitHub | 工程以 PR 为准即可 |
| 文档 | Google Docs、Notion、Confluence | 任务回链 |
| 设计 | Figma | 标注能被读最好 |
| 会议/日历 | Zoom + Google Calendar | 要转写才能自动化 |
| 代码 | GitHub、GitLab | 提示词和评测也入库 |
| 编码助手 | Cursor、Codex、Claude Code | 读同一套仓库规则 |
| 对话观测 | Langfuse、LangSmith | 生产流量尽量全量 |
| 产品观测 | Datadog、Grafana | 验收标准和告警对得上 |
| 分析 | Metabase、Looker | Agent 只用审过的问题 |
| CMS | Contentful 等 | AI 只出草稿 |
| 功能开关 | 自建或 Flag 产品 | Copilot 能随时关 |
| CRM | Salesforce、HubSpot | 默认只读 |
| 人事 | Rippling、Workday 等 | 入离职驱动开通吊销 |
| 合同/Offer | PandaDoc、DocuSign | 发送必须人审 |
| 编排 | 对话 SDK；n8n / Temporal | 产品对话和组织胶水分开 |

两周内只做六件事就够：反馈频道和任务标签；人和 Bot 两套身份；保险库把模型 key 收起来；消息先分类再人工确认建单；接通对话观测并准备几十条金标；接口目录先空着，但开始登记。

## 默认红线

厂商原始 key 只留在保险库，运行时按环境注入。应用不要直接持有 `OPENAI_API_KEY` 这类东西。

对外发送、发布、删数据、高敏感字段，默认等人确认。数字结论要带上来源（看板问题、文档、任务编号）。提示词、Agent 配置、评测集走 Git。审计日志不能由 Agent 删除。

---

## 可以按这个顺序长

1. 仓库规则、文档跟 PR、最小验证。没有这一步，后面都是加速出错。
2. 产品 Copilot：入口、上下文、开关、trace。
3. 密钥和环境隔离。有余力再上网关。
4. 反馈进任务。人工确认按钮先开着。
5. 会议和日历。
6. CRM / 人事 / 合同。先读后写，写一定要人审。

新成员第一周如果能做到：查到最近的决策、按规则开 PR、问到带来源的指标，这套基建就算开始工作了。
