# AI Native 组织基建 Handbook

这份文档给技术团队做 onboarding：公司里要有哪些系统、每个系统干什么、工作怎么在系统之间转、Agent 实际怎么跑（包括改数据库、改登录鉴权这种危险操作）、以及你怎么从零搭起来、日常怎么用。

工具可以换成等价产品。下面用一套常见组合举例，方便对照采购和接线。换品牌时，表里的「职责」不要删。

读完你应该能回答四件事：

1. 一个需求从提出到上线，经过哪些系统。
2. 编码 Agent、产品 Copilot、Slack Bot 各走哪条链路，权限边界在哪。
3. 迁移和鉴权为什么不能让 Agent 自己拍板，正确流程是什么。
4. 新团队第一周、第一个月分别要装什么、配什么、教什么。

---

## 1. 系统全景

把组织看成一条流水线，而不是一堆 SaaS 图标。人、Agent、服务账号都从左边进，结果落到右边的「可追踪记录」上。

```text
                    ┌──────────── 身份与密钥 ────────────┐
                    │  SSO（人）  M2M（机器）  保险库     │
                    │  密钥网关（逻辑 key、限额、吊销）    │
                    └───────────────┬───────────────────┘
                                    │ token / 逻辑 key
┌─────────── 信号进场 ───────────┐  │  ┌──────── 执行与交付 ────────┐
│ Slack 反馈 / 工单 / CRM 缺口    │  │  │ Git 仓库 + PR + CI         │
│ 会议转写 / 日历事件             │──┼─▶│ 编码 Agent（编辑器里）      │
│ 产品页面上下文 / 用户提问       │  │  │ 产品 Copilot（App 内）      │
│ 监控告警                        │  │  │ 工作流引擎（n8n 等）        │
└────────────────────────────────┘  │  └────────────┬───────────────┘
                                    │               │
                                    │               ▼
                                    │  ┌──────── 业务系统 ─────────┐
                                    │  │ 应用 API / DB / CMS / CRM │
                                    │  │ Feature Flag / 对象存储    │
                                    │  └────────────┬───────────────┘
                                    │               │
                                    ▼               ▼
                    ┌──────────── 观测与记录 ───────────┐
                    │ Trace（Langfuse）  APM（Datadog）  │
                    │ 任务（Linear/Jira/GitHub） 文档     │
                    │ 审计日志（谁调了什么、是否人审）     │
                    └───────────────────────────────────┘
```

三句话串起来：

- **身份层**决定谁可以调工具。人用 SSO；Agent 用短时机器凭证，scope 写死。
- **执行层**真正改代码、回消息、写草稿。编码 Agent 改仓库；产品 Copilot 走应用 API；组织 Bot 调 Slack / 任务系统 / 日历。
- **记录层**让结果可复查。没有任务编号、PR、trace、审计，这次操作等于没发生。

## 2. 工具地图：每类工具承担什么

按职责分组。同一职责不要买两套「官方真相」，否则 Agent 不知道信哪一个。

### 2.1 身份、密钥、策略

| 职责 | 典型产品 | 在流水线里做什么 | Agent 默认权限 |
|------|----------|------------------|----------------|
| 员工登录 / SSO | Auth0、Okta | 人进内部工具、云控制台、Bot 管理后台 | 不给 Agent 用员工密码 |
| 机器身份 | 同一套 IdP 的 M2M | Slack Bot、CI、Copilot 后端用 client credentials 换短时 token | 每个 Agent 一个 client，scope 最小化 |
| 密钥存放 | 1Password、Bitwarden | 存厂商原始 key、数据库密码、Auth0 secret | Agent 禁止列出保险库 |
| 运行时密钥 | AWS Secrets Manager、同类 secret 服务 | 按环境注入 `local` / `staging` / `prod` | 只读当前环境需要的那些 |
| 模型/SaaS 出口 | 自建网关、LiteLLM、Portkey | 统一 baseURL、限额、模型白名单、按 agent 计费 | 只持有逻辑 key，不持有 `OPENAI_API_KEY` |
| 策略 | 网关规则 + IdP Action | 发布、对外发送、删数据：拒绝或要求人审 | 无对应 scope 必须失败，不能静默降级成「试试看」 |
| 审计 | Datadog Logs / 数仓 | 记录 actor、action、resource、是否人审、trace id | Agent 不能删除审计 |

本地开发常见接法：保险库或 secret 服务生成一份环境文件；个人覆盖用单独的 overrides，不要改共享 secret。云上按服务拉取：应用拉应用 secret，再按需拉数据库 secret。

### 2.2 协作与任务

| 职责 | 典型产品 | 在流水线里做什么 |
|------|----------|------------------|
| 即时沟通 | Slack | 反馈入口、事故频道、会前简报、Bot 回帖 |
| 任务队列 | Linear、Jira、GitHub Issues | 产品需求和缺陷；字段里留下源链接 |
| 工程交付 | GitHub / GitLab | 分支、PR、CI、代码评审机器人 |
| 文档 | Google Docs、Notion、Confluence | Spec、ADR、runbook；任务和 PR 必须回链 |
| 设计 | Figma | 约束和标注；「ready for eng」可以触发拆任务 |
| 会议 | Zoom + 转写 | 会后抽决策和 action |
| 日历 | Google Calendar | 会前 T-30min 触发简报；迭代起止触发摘要 |

约定：工程是否合并，以 PR 为准。任务系统负责「要不要做、谁做、做到哪」。两套都有没问题，但不要让会议纪要成为第三套待办本。

### 2.3 数据、内容、外部业务系统

| 职责 | 典型产品 | 在流水线里做什么 | 注意 |
|------|----------|------------------|------|
| 业务数据库 | PostgreSQL 等 | 产品数据、迁移 | Agent 改 schema 见第 4.3 节 |
| CMS | Contentful | 运营内容 | AI 只建草稿，发布要人 |
| 功能开关 | 自建 flag 或 LaunchDarkly | Copilot 和风险功能可关 | 新 Agent 能力默认关 |
| 分析 | Metabase、Looker | 审过的问题/看板 | 禁止自由 SQL |
| 检索 | Algolia / ES | 文档和历史反馈查重 | 写入只用管道账号 |
| CRM | Salesforce、HubSpot | 客户/机会上下文 | 读可以自动；改金额/关单要人 |
| 客服 | Front、Zendesk | 工单摘要、回流缺陷 | 回复默认草稿 |
| 人事 | Rippling、Workday | 入职开通、离职吊销 | 薪酬不进公开频道 |
| 合同 | PandaDoc、DocuSign | Offer / NDA / MSA 草稿 | 发送、作废要人 |

### 2.4 模型、编排、观测

| 职责 | 典型产品 | 在流水线里做什么 |
|------|----------|------------------|
| 编码助手 | Cursor、Claude Code、Codex | 读仓库规则，改代码，跑测试，开 PR |
| 产品对话 | Vercel AI SDK 或同等流式 SDK | App 内 Copilot，SSE + 工具调用 |
| 组织编排 | n8n、Temporal、LangGraph | Slack/日历/CRM webhook → 多步流程 |
| 对话观测 | Langfuse | prompt 版本、trace、人工打分、坏例集 |
| 评测 | 仓库内 harness + CI | 改 prompt/路由必须能回归 |
| 产品观测 | Datadog | 延迟、错误、业务埋点、告警 |
| CI | GitHub Actions 等 | lint、测试、密钥扫描；Agent 相关路径可加评测门禁 |

## 3. 工作怎么转起来

下面五条是默认主路径。新团队先打通 A 和 B，再做 C。

### A. 工程师改产品（每天最多的路径）

```text
需求出现在任务系统或口头（口头必须补任务）
  → 人在编辑器里开编码 Agent，贴任务链接和验收标准
  → Agent 读仓库规则（根目录流程 + 当前应用目录的命令/边界）
  → 只改相关目录，跑该目录最小检查
  → 若改了规则/权限/状态机：同一 PR 更新领域文档
  → 推分支、开 PR（摘要 / 怎么验的 / 文档 / 风险）
  → CI + 自动审查
  → 人合并；功能开关灰度；看板对照验收
```

### B. 用户在产品里问 Copilot

```text
用户打开抽屉 / 页面助手
  → 前端带上：消息、已选对象（学生/客户等）、文档、当前页面摘要
  → POST 到应用后端（例如 /copilot），流式返回
  → 后端用机器身份调模型网关，按入口选择工具集
  → 工具调用走业务 API（查数据、生成文档草稿），不直连数据库超级账号
  → 线程和消息写入业务库
  → Langfuse 记 trace；开关可一键关掉入口
```

### C. Slack 反馈进研发

```text
#feedback 新消息
  → Bot 拉消息和线程 → 脱敏
  → 分类（缺陷/需求/咨询/事故）+ 严重度 + 产品面
  → 任务系统和检索里查重
  → 把握低：线程追问；把握高：建任务并回链
  → P0 / 付款 / 安全：只建单 + 打 #incidents，不改生产
  → 每天一条摘要给人审误判
```

### D. 会议变成任务

```text
日历：会议结束 或 转写就绪
  → 拉转写 → 抽出 decisions / action_items / risks
  → 每个 action 必须有负责人邮箱，猜不准就标未指定
  → 写进任务系统，链回到日历或文档
  → 会前 T-30min：把相关任务和上次结论推进频道
```

### E. 密钥与账号生命周期

```text
入职（人事系统事件）
  → 开 SSO、邮箱、Slack、Git、任务系统、保险库分组
  → 按角色模板给模型逻辑 key 的档位（dev 有、prod 无）

申请新模型或新 SaaS
  → 登记到接口目录（谁拥有、什么权限、PII 级别、限流）
  → 原始 key 进保险库 → 网关注册逻辑 key

离职
  → 即时吊销 SSO、Git、生产权限、逻辑 key、M2M client
  → 开放任务转交
  → 吊销失败当 P0
```

## 4. Agent 到底怎么运转

### 4.1 先分清三种运行实体

| 名称 | 宿主 | 读什么 | 允许写什么 | 典型身份 |
|------|------|--------|------------|----------|
| 编码 Agent | Cursor / Claude Code 等 | 仓库、本地文件、你配的 MCP | 工作区文件、测试、git（按规则） | 就是你的员工 SSO + 本地凭据 |
| 产品 Copilot | 网页/App | 请求里的上下文 + 业务 API | 业务库里的线程/草稿；发布类操作要人 | 后端 M2M |
| 组织 Bot | Slack / 工作流引擎 | 频道、日历、任务 API | 回帖、建任务、写草稿 | 独立 M2M，scope 更窄 |

不要让同一个 token 既能改生产数据库、又能在 Slack 闲聊。出事时你撤不掉「那一个密钥」。

### 4.2 编码 Agent：一次任务的内部步骤

人发：「按这个任务做，验收是……」之后，合格的编码 Agent 应按仓库规则走，而不是直接开写。

```text
1. 定位
   读根目录规则：分支、提交、验证、文档、高风险清单
   读当前应用目录规则：技术栈、测试命令、目录边界
   只打开和任务相关的文件，禁止全仓无目的遍历

2. 改
   默认单应用。前后端都要动，拆成可审查的两次提交或明确写在 PR 里
   不碰：环境加载脚本、部署脚本、bootstrap——除非任务就是这个

3. 验
   跑「被改到的那个包」的最小检查（类型、lint、相关测试）
   全仓本来就红、且与本次无关：写进 PR，不要写成「全绿」

4. 文档
   权限、可见性、状态流转、校验、副作用变了 → 改领域文档 + 追加变更日志
   没变 → PR 里写「文档无需更新，因为……」

5. 交
   从最新主干拉分支；一次一事；按团队前缀和 conventional commit
   开 PR，处理自动审查里能确定的问题
```

编码 Agent 用的是**开发者自己的权限**：能碰到你本机的环境文件、云登录、数据库。所以规则必须写清哪些事停下来问人。下一节就是这些事。

### 4.3 迁移（数据库 schema / 数据回填）

迁移会改所有环境的数据结构，回滚成本高，Agent 最容易「顺手加一列」。

**什么算迁移任务**

- 新建表、加列、改类型、加索引
- 数据回填、从旧列拷到新列
- 改唯一约束、外键、枚举值
- 种子数据、权限相关表

**强制流程**

1. Agent 识别到上述改动，先停。用人类能回答的方式问：要不要做、表名/列名是否已定、是否需要 backfill、回滚怎么做。
2. 人明确同意后，才生成迁移文件。必须同时有 `up` 和 `down`（或团队规定的等价回滚）。
3. 禁止改已经上线环境执行过的旧迁移文件。只能新增。
4. 数据迁移用事务；大批量回填要可重跑，不要写一次性不可恢复脚本。
5. 本地先 `migrate`，再跑相关集成测试。需要的话演示 `rollback`。
6. PR 里单独列出：影响哪些表、是否 lock、是否 backfill、回滚步骤、是否要 DBA/负责人点头。
7. 合并后按环境执行：dev → staging → prod，不要让 Agent 直接打生产。

**Agent 可以做的**

- 按现有迁移风格起草文件
- 补索引说明、类型映射
- 写回填脚本草稿和测试

**Agent 不能做的**

- 自己决定「这个字段没用了，drop 掉」
- 在生产库执行 migrate
- 把密钥写进迁移或 seed
- 为了图省事改历史迁移哈希

### 4.4 鉴权、授权、密钥

这里的「鉴权」包括：登录、session、token、角色、对象级权限、密钥加载。

**为什么单独列**

鉴权 bug 的形态是「看起来功能好了，但别人能看见不该看见的数据」。测试如果只测 happy path，Agent 会交一份能演示、不能上线的 PR。

**改鉴权时 Agent 必须先搞清的问题**

- 谁是调用方：浏览器用户、内部员工、M2M、匿名？
- 凭证从哪来：cookie、Bearer、SSO code、client credentials？
- 授权模型：角色、资源上的 relation、还是硬编码名单？
- 失败时：401、403、还是静默空列表？（空列表会把漏洞藏起来）
- 有没有对象级检查：能不能用别人的 id 把资源读出来？

**强制流程**

1. 停下来复述将要改变的登录/权限行为，等人确认。包括：哪些角色可见、哪些 API 要登录、是否破坏现有 session。
2. 不改密钥加载入口、不改「从哪里读环境变量」的引导脚本，除非任务就是修这个。
3. 不把真实 secret 写进仓库、示例、文档、Agent 工作日志。示例只用占位符。
4. 新增 API 默认：先鉴权，再鉴权对象归属，再执行业务。
5. 测试至少覆盖：未登录、错误角色、跨对象 id。不要只有「登录用户成功」。
6. 机器账号：Copilot 后端用独立 M2M，不要复用员工 token 去打内部管理接口。
7. 密钥轮换：改保险库 → 运行时重载 → 审计 `key.rotated`。泄露则先吊销逻辑 key，再换厂商 key。

**产品 Copilot 的鉴权**

```text
浏览器用户 SSO/session
  → 前端 fetch /copilot 带用户 cookie
  → API 确认用户身份和「能否访问上下文里那个对象」
  → 再换 M2M 去调模型网关
  → 工具层继续用「该用户」的数据权限，而不是超级账号
```

常见错误：Copilot 后端用一个万能数据库账号把任意学生档案塞进上下文。正确做法是工具查询走和普通 API 相同的授权函数。

**组织 Bot 的鉴权**

- Slack 用户映射到员工身份，再决定能否查指标、建任务。
- 建任务可以；改 CRM 金额、发正式合同、发布 CMS，默认拒绝或人审。
- `publish` / `admin` scope 不要发给对话用的那个 Slack app。

### 4.5 产品 Copilot：一次请求怎么走

以「页面右侧助手」为例。

**入口**

一个产品里可以有多个入口，例如通用助手、引导流程、某个岗位的专用助手。入口决定：系统提示、能否生成文档、调哪些工具。用功能开关包住整个入口。

**上下文**

| 类型 | 来源 | 注意 |
|------|------|------|
| 对象上下文 | 用户当前选中的客户/学员等 | 先做对象级授权再序列化 |
| 文档上下文 | 已关联的材料 | 限制条数和体积 |
| 页面上下文 | 当前路由 + 可见区域摘要 | 发送时再取；敏感字段可脱敏；不要把整页 DOM 持久化到本地 |

**状态**

- 需要跨刷新保留的：抽屉是否打开、当前线程、用户偏好。可放本地持久化，但去掉 React 节点这类不能序列化的东西。
- 只在一次会话有效的：正在生成、临时 flag。不要写进 localStorage。

**后端**

- `POST /copilot`（或按入口分路径），`text/event-stream`
- 请求体：messages、contexts、入口、可选 pageContext
- 工具调用：查业务、写草稿、列线程；写生产配置要人审或走单独 mutation
- 线程/消息落业务库，方便刷新和审计

**观测**

至少打这些事件：消息提交、首 token、成功、失败、重新生成。trace id 和用户、入口、线程一起进 Langfuse。

### 4.6 组织 Bot：一次反馈怎么走

```text
ingest → 规则预处理（去表情、抽环境/版本）
      → LLM 分类（走网关，带 schema）
      → 查重
      → 在线评分（缺复现步骤？含 PII？该不该做？）
      → 建任务或追问
      → Slack 回帖（含按钮：确认 / 不是重复 / 转人工）
      → 写审计 + trace
```

置信度低于阈值就不要自动建单。转人工之后状态机停在收集，不再改任务状态。

## 5. 仓库里要先放齐的「给 Agent 的说明书」

没有这些文件，编码 Agent 每次都会猜流程。建议最少：

```text
/
  AGENTS.md                 # 全仓：分支、验证、文档、高风险、PR 格式
  docs/
    business-map.md         # 业务域指路
    domains/*.md            # 每个域的规则：权限、状态、副作用
    log.md                  # 只追加的变更记录
  apps/web/AGENTS.md        # 前端命令、目录、测试
  services/api/AGENTS.md    # 后端命令、模块结构、迁移约定
  <feature>/AGENTS.md       # 某个 Copilot 的入口、上下文、接口
  .agents/skills/           # 可复用操作手册（可选）
```

根目录规则建议写死这些条款（按你司命名改即可）：

- 不直接提交主干
- 先更新远端主干再开分支
- 一次提交只做一件事
- 只暂存本次相关文件
- 每个被动到的包跑最小验证
- 改了已文档化的行为，必须改对应 domain 文档
- 迁移 / 鉴权 / 计费 / 权限 / 部署：先问人
- PR 必须有：摘要、改了什么、怎么验的、文档、风险

## 6. 怎么搭建（按阶段，可当项目计划）

### 第 0 周：能让编码 Agent 按规矩交活

1. 写根目录 `AGENTS.md` 和各应用一份。
2. 规定分支名、PR 模板、CI 最小集（lint/test/secret scan）。
3. 业务文档开始当交付物，而不是「有空再写」。
4. 全员编辑器装同一类编码助手，打开仓库规则自动生效。
5. 密钥：每人能从保险库或 `get-env` 等价脚本拿到本地环境，禁止在群里发 key。

验收：任意工程师用 Agent 做一个小改动，PR 里能看到验证和文档判断。

### 第 1–2 周：产品 Copilot 最小闭环

1. 后端一条流式接口 + 机器身份调模型。
2. 前端抽屉：发消息、展示流式结果、落线程。
3. 一种上下文（例如当前对象）+ 授权检查。
4. 功能开关默认关，内测名单开。
5. Langfuse：请求打上 trace。

验收：内测用户能问到「和当前对象有关」的答案；关掉开关入口消失。

### 第 3–4 周：身份与模型出口收口

1. 人和 Bot 在 IdP 里拆开应用。
2. 原始模型 key 只留保险库和网关。
3. 应用只配逻辑 key + 网关 baseURL。
4. 审计至少能查：哪个 agent、哪个模型、多少 token。

验收：开发机和 CI 里搜不到厂商原始 key；吊销逻辑 key 后 Bot 立刻调不通。

### 第 2 个月：反馈进任务

1. Slack 频道 + Bot 订阅。
2. 分类 schema 固定。先人工点确认再建任务。
3. 30–50 条金标，分类错误能被测出来。
4. PII 检测：原文不进任务描述。

验收：中位首次回复小于两分钟；人 24 小时内改类型的比例可接受（例如低于 20%）。

### 之后才做

会议入库、CRM 简报、人事开通吊销、合同草稿。每一项都是「先只读，写操作人审」。

## 7. 日常怎么用

### 工程师接到一个普通功能

1. 打开任务，确认验收标准和范围外。
2. 在仓库根目录开 Agent，说明「只改哪个应用」。
3. 让 Agent 先列要动的文件和风险，再写代码（迁移/鉴权直接进第 4.3 / 4.4 节）。
4. 本地跑它提示的那条测试命令，你自己再点一次主路径。
5. 看 diff：有没有多余格式化、有没有动到无关文件。
6. 开 PR。自动审查说得对就改；拿不准 @ 给人。

### 工程师接到「加一列并回填」

1. 你先定：列类型、默认值、是否 null、是否回填历史、锁表窗口。
2. 明确对 Agent 说：可以起草迁移，不要执行生产，不要改旧文件。
3. 你在本地 migrate + rollback 走一遍。
4. PR 标数据负责人。

### 工程师接到「某个角色不能再看见 X」

1. 先在领域文档里找到当前可见性规则。没有就先补文档再改代码。
2. 让 Agent 改授权函数和测试：原角色 403 或空列表（按产品决定，不要两者混用）。
3. 用两个账号或两个 fixture 验证跨对象访问。
4. 同一 PR 更新领域文档。

### PM / 设计怎么用

- Spec 用固定标题：问题、用户、场景、验收、范围外、指标、Agent 要不要新工具。
- 设计标注写清状态和空态，避免 Agent 只实现视觉稿。
- 不要把生产 key 贴进文档。

### 值班

- Copilot 异常：关功能开关，再查 Langfuse 和 APM。
- Bot 乱建任务：关自动建单，保留收集。
- 密钥疑似泄露：网关吊销 + IdP 废 token + 开事故频道。

## 8. 接口目录（给网关和 Bot 用）

每个允许 Agent 调用的能力登记一行：

| 字段 | 含义 |
|------|------|
| endpoint_id | 稳定 ID |
| system | github / slack / metabase / crm … |
| 调用方式 | HTTP path 或 MCP tool 名 |
| auth | IdP scope 或网关策略 |
| secret_ref | 保险库/网关逻辑名 |
| access_level | read / draft_write / publish / admin |
| pii_class | none / low / high |
| allowed_agents | 白名单 |
| rate_limit | 日限额 |
| owner | 负责人 |
| runbook | 故障怎么关 |

没进目录的接口，对 Agent 视为不存在。需要新能力时走申请，不要在对话里塞一把万能 key。

## 9. 红线（写进仓库规则，而不是口头）

1. 厂商原始 key 只出现在保险库和密钥运行时，不出现在前端、文档、Replit 类沙箱明文里。
2. 迁移、鉴权、计费、权限模型、部署脚本：Agent 先问后改。
3. 已执行的历史迁移文件不改。
4. Copilot 工具查询复用普通 API 的授权，不用超级账号。
5. 对外发送、CMS 发布、合同发送、CRM 关单：默认人审。
6. 指标数字必须带来源 ID。
7. 审计日志 Agent 不可删。
8. 工作记录不贴聊天原文和密钥。

## 10. 新成员第一周清单

**第 1 天**

- SSO、Git、保险库、本地环境脚本跑通
- 编辑器打开本仓库，确认根目录规则被加载
- 用两个测试账号登录应用，体会角色差异

**第 2–3 天**

- 跟一个小任务走完：Agent 改代码 → 最小测试 → PR
- 读业务地图和自己负责的 domain 文档
- 看一次 Copilot 的 Langfuse trace

**第 4–5 天**

- 故意走一遍「迁移或鉴权」模拟：看 Agent 会不会停下来问你
- 知道事故时关 Copilot 开关和吊销逻辑 key 的人是谁

到这里，你不是「会用聊天窗口的人」，而是这套流水线上的操作者。之后加 Slack Bot、会议入库，都是在同一条身份和记录层上接新的执行器。
